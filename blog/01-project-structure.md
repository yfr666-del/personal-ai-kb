# 为什么我这样设计目录结构

> 第一篇项目笔记。记录我在动手写第一行代码之前，是怎么想清楚「文件该放哪」这件事的。
> 项目：personal-ai-kb（个人 AI 知识库系统）　阶段：M1 骨架 v0.1

---

## 一、我要做的是什么

我要给自己做一个知识库。平常看的 PDF、写的笔记、收藏的网页，散在好几个地方，想找的时候翻半天。市面上的笔记软件也能搜，但只能按**关键词**搜 —— 我常常只记得大概意思，不记得原话，就搜不出来。

所以我想做一个能按「意思」搜的东西：我把资料丢进去，用大白话问它，它翻出相关内容回答我，而且必须告诉我这句话是从哪份文件的哪一页来的。

自己的东西自己造一遍，也比直接用现成的黑盒更有底。

---

## 二、第一个纠结：要不要一开始就上框架

我做这个项目时，第一反应也是「找个 LangChain 的 RAG 教程抄一套」。但我最后决定先用原生 Python 写，理由是：

1. **我想讲得清每一步在干嘛。** 框架把「检索」包成了一行调用，用起来快；但如果有人指着我的项目问「你的检索是怎么实现的、为什么这么设计」，我只能回答「框架里就是这么做的」。
2. **我想知道自己哪里不懂。** 框架藏起了大量细节，出问题时我不知道该看哪儿。先用原生写一遍，等于把路亲自走一遍，之后再引入框架，才知道它替我做了什么、又藏了什么。

## 三、我的分层，以及每层为什么存在

| 目录 | 放什么 | 为什么它要单独一层 |
|---|---|---|
| `app/api/` | HTTP 路由、参数接收 | HTTP 相关的东西只出现在这里，别的层不知道「这是个从网页来的请求」。以后要是改成命令行工具，只换这一层 |
| `app/models/` | Pydantic 模型、所有校验规则 | 规则集中一处，改白名单不用满项目找，也能被多个入口共用 |
| `app/core/` | 配置（读 `.env`） | 会随环境变化的东西（密钥、地址、参数）只有这一个出口，其他地方不许硬编码 |
| `app/services/` | 切分、检索、调 LLM（M2 才填） | 这一层是纯业务，不该知道「HTTP 是什么」，方便单独测试和复用 |

## 四、一个真实的小决定：校验规则放哪

一开始，我把文件名后缀的判断直接写在接口函数里：

```python
# 反例：规则和接口糊在一起
@router.post("/upload")
async def upload_document(file: UploadFile):
    if not file.filename.endswith((".pdf", ".txt", ".md")):
        raise HTTPException(status_code=400, detail="只支持 .pdf / .txt / .md")
    ...
```

后来改成了集中写进模型：

```python
# app/models/document.py
ALLOWED_SUFFIXES = (".pdf", ".txt", ".md")


@field_validator("filename")
@classmethod
def check_filename(cls, v: str) -> str:
    if "/" in v or "\\" in v:
        raise ValueError("文件名不能包含路径分隔符")
    if not v.lower().endswith(ALLOWED_SUFFIXES):
        raise ValueError(f"只支持 {'、'.join(ALLOWED_SUFFIXES)} 格式")
    return v
```

换来的好处：

1. **规则只有一处。** 明天要加 `.docx` 支持，改元组那一行就够了；照原来的写法，得把所有出现过后缀判断的地方挨个翻出来改。
2. **多个入口自动共用。** 上传接口要校验，将来「用户手动改文件名」也要校验 —— 规则写在模型里，两边同时生效，不会漏改一个。
3. **终于能写测试了。** 规则集中在模型里，我才能用 pytest 一条一条地测（现在有 12 个用例）；散在接口里，就只能靠手点页面，改一次点一次。

## 五、踩到的坑

**坑 1：`.env` 差点被提交上去**

`.env` 里放着我的 API Key。我一开始把配置直接写在代码里，后来才搬到 `.env` —— 搬完差点忘了屏蔽它。如果就这么 push 到公开仓库，等于把家里钥匙挂在大门上，别人拿去就能刷我的额度。

解决办法：把 `.env` 写进 `.gitignore`，仓库里只留一个不含真实值的 `.env.example`，新克隆的人照着模板填自己的。

**坑 2：学习用的草稿脚本和产品代码混在根目录**

我一边学 Pydantic，一边随手写练手脚本（`learn_pydantic.py`、`dictation.py`、`check_models.py`），全扔在项目根目录。仓库公开后才意识到：别人 clone 下来，第一眼看到的是满屏学习草稿，分不清哪部分是真正的项目代码。

学习痕迹本身不是坏事，但它应该有自己的位置，而不是和产品代码混在一起。
